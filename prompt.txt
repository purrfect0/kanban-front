## 2. Назначение продукта

Это внутренняя канбан-доска команды SSJCorp.

* разработкой сайтов;

## 3. Технологический стек

Обязательный стек:

* Next.js с App Router;
* TypeScript в строгом режиме;
* Tailwind CSS;
* Magic UI:
  https://magicui.design/docs/components
* Lucide React для иконок;
* `@dnd-kit/core` и `@dnd-kit/sortable` для drag-and-drop;
* `localStorage` как временное frontend-хранилище;
* npm как package manager.

Для доступных диалогов, dropdown, tooltip, sheet и popover разрешено использовать shadcn/ui или Radix UI. Magic UI используй для фирменных визуальных эффектов и анимаций, а не вместо всех базовых UI-примитивов.

Не подключай backend, базу данных, Firebase, Supabase, серверную авторизацию или фиктивные сетевые запросы к несуществующему API.

### 6.2. Канбан-доска

Маршрут `/board/`.

Выбранный проект должен синхронизироваться через query-параметр, например:

`/board/?project=ssjcorp-site`

При отсутствии параметра используй последний выбранный проект из `localStorage`.

Стандартные колонки:

1. «Бэклог»
2. «К выполнению»
3. «В работе»
4. «На проверке»
5. «Готово»

Для каждой колонки:

* заголовок;
* количество карточек;
* необязательный WIP-лимит;
* кнопка быстрого создания задачи;
* drag-and-drop внутри колонки;
* перенос карточек между колонками;
* заметная, но не агрессивная drop-zone;
* пустое состояние;
* возможность свернуть колонку на desktop.

Обеспечь горизонтальную прокрутку только внутри области доски. Sidebar и верхняя панель не должны прокручиваться вместе с колонками.

Карточка задачи должна показывать:

* ID, например `WEB-024`;
* название;
* краткое описание максимум в две строки;
* приоритет;
* метки;
* исполнителей;
* срок;
* состояние срока: нормально, скоро, сегодня, просрочено;
* прогресс чек-листа;
* оценку времени;
* признак блокировки;
* иконку количества вложений как демонстрационное поле, без загрузки файлов.

Используй следующие приоритеты:

* P0 — критический;
* P1 — высокий;
* P2 — обычный;
* P3 — низкий.

Не передавай смысл только цветом: показывай текст или иконку вместе с цветом.

При клике по задаче открывай правую `Sheet`-панель с подробностями.

В панели задачи должны работать:

* редактирование названия;
* описание;
* смена колонки;
* выбор приоритета;
* назначение исполнителей;
* выбор срока;
* редактирование меток;
* оценка времени;
* создание, выполнение и удаление пунктов чек-листа;
* отметка «Заблокировано» с короткой причиной;
* удаление задачи с подтверждением;
* сохранение изменений;
* закрытие по Escape;
* предупреждение при закрытии с несохранёнными изменениями.

Добавь создание новой задачи через полноценную форму с валидацией.

## 9. Magic UI и анимации

Используй Magic UI осмысленно. Анимации должны помогать восприятию состояния, а не отвлекать от работы.

Применение компонентов:

* `AnimatedGridPattern` — очень слабо заметный фон на экране обзора и в пустых состояниях;
* `MagicCard` — карточки проектов на экране обзора;
* `BlurFade` — первичное появление блоков обзора и колонок доски;
* `NumberTicker` — четыре верхних показателя;
* `AnimatedThemeToggler` — переключение темы;
* `BorderBeam` — только для активного проекта или одного важного элемента, без обводки каждой задачи;
* `RippleButton` или аналогичный Magic UI button — основные действия «Новая задача» и «Создать проект».

Для drag-and-drop используй естественную анимацию через dnd-kit:

* карточка слегка приподнимается;
* появляется корректный `DragOverlay`;
* место вставки видно;
* соседние карточки плавно перестраиваются;
* никаких скачков layout;
* после переноса карточка остаётся в новой позиции.

Ограничения:

* микровзаимодействия 150–300 ms;
* сложные переходы не длиннее 400 ms;
* анимируй преимущественно `transform` и `opacity`;
* не анимируй размеры, вызывая layout shift;
* не добавляй Meteors, Particles, Aurora Text и другие декоративные эффекты на рабочую доску;
* не анимируй каждую карточку бесконечно;
* реализуй `prefers-reduced-motion`;
* при reduced motion отключай фоновые и вступительные анимации;
* интерфейс должен оставаться полностью доступным во время анимаций.

## 11. Состояние и подготовка к backend

Временно сохраняй всё состояние в `localStorage`.

Используй версионированный ключ, например:

`ssjcorp-kanban:v1`

Демо-данные загружай только при первом открытии. Не перезаписывай пользовательские изменения при каждом перезапуске.

Добавь в настройки или меню пользователя действие «Сбросить демо-данные» с подтверждением.

Архитектура должна позволять позже заменить `localStorage` на backend без переписывания UI.

Создай:

* строгие доменные типы `Project`, `Task`, `Column`, `Member`, `Label`, `ChecklistItem`;
* интерфейс репозитория данных, например `KanbanRepository`;
* асинхронные методы репозитория;
* реализацию `LocalStorageKanbanRepository`;
* отдельный слой hooks/services, через который UI работает с данными;
* централизованный store или Context;
* отдельные seed-данные;
* константы статусов и приоритетов;
* утилиты расчёта прогресса и состояния дедлайна.

UI-компоненты не должны напрямую обращаться к `localStorage`.

Не создавай фальшивый API-клиент, который отправляет запросы в никуда. В README опиши, в каком месте товарищ сможет добавить `ApiKanbanRepository`.

* использовать актуальную LTS-версию Node.js;
* выполнять `npm ci`;
* выполнять проверки;
* выполнять `npm run build`;
* загружать каталог `out`;
* публиковать его через официальные GitHub Pages actions;
* иметь permissions:

  * `contents: read`;
  * `pages: write`;
  * `id-token: write`;
* использовать environment `github-pages`;
* иметь concurrency, не допускающий конфликтующих деплоев.

Используй официальные actions:

* `actions/checkout`;
* `actions/setup-node`;
* `actions/configure-pages`;
* `actions/upload-pages-artifact`;
* `actions/deploy-pages`.

Если есть административный доступ, выбери в настройках репозитория:

`Settings → Pages → Build and deployment → Source → GitHub Actions`.

Если доступа недостаточно, не утверждай, что деплой завершён. Сообщи точный недостающий шаг и продолжи всё остальное, что возможно.

## 16. Критерии готовности

Работа считается выполненной только если:

## 17. Git и финальный отчёт

После успешной проверки:

1. Добавь все необходимые файлы.
2. Создай осмысленный коммит, например:
   `feat: build SSJCorp kanban frontend`
3. Отправь изменения в `main`.
4. Дождись завершения GitHub Actions.
5. Проверь опубликованный сайт.
6. Если deployment упал, изучи логи, исправь причину, снова закоммить и дождись успешного результата.

В финальном ответе обязательно укажи:

* что реализовано;
* URL GitHub Pages;
* URL репозитория;
* commit SHA;
* статус lint, typecheck и build;
* статус GitHub Actions;
* какие данные сейчас хранятся локально;
* где подключать будущий backend;
* есть ли действия, которые владелец репозитория должен выполнить вручную.

Не задавай уточняющих вопросов, если можешь принять разумное техническое решение самостоятельно. Не останавливайся на плане — реализуй, проверь, закоммить, опубликуй и только после этого предоставь отчёт.
